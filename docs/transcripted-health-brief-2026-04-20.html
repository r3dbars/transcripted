Main Issue

This is the first thing I would fix.

APPLE-MACOS-V
Fix now

parakeet.audio_engine_start_failed

This is a real core-workflow bug, not instrumentation noise. It fires when dictation tries to start the speech audio engine and AVAudioEngine.start() fails after tap setup.

  • 111 production events, first seen Apr 20 at 9:35 AM CDT.
  • 100% of the issue is tagged release=transcripted@1.1.12.
  • Event context says Parakeet was loaded, meeting state was ready, and STT was not already recording.
Likely area

Audio graph lifecycle around dictation start

The relevant code path is Sources/Speech/ParakeetEngine.swift: it installs an input tap, prepares the engine, then starts it. A failure removes the tap and returns false, but it does not yet look like a full graph rebuild/retry path.

  • Pair this with APPLE-MACOS-J, a fatal CoreAudio installTap issue seen on nearby releases.
  • Add privacy-safe context only: route/device class, sample rates, channel counts, prewarm state, retry count.
  • Do not send transcript text, audio paths, meeting titles, names, emails, or absolute file paths.

What To Fix

Ranked by user pain, confidence, and fix leverage.

1. Ship

Audio-engine start recovery

Add a bounded recovery path around Parakeet dictation start: remove tap, stop/reset or recreate the engine, re-read formats, retry once, and report a clearer permanent failure if it still cannot start.

2. Cover

Short-recording UX

Promote recording_too_short into a deliberate UI state for meetings. Keep the analytics, but stop making a predictable bad-input path feel like a broken app.

3. Set up

Release and site telemetry

Watch 1.1.13 for another 24 hours, then cut 1.1.14 if the audio fix lands. Also enable Cloudflare Web Analytics or grant read scope so product-site traffic is visible.
