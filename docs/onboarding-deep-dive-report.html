Transcripted onboarding audit

The current onboarding is clear enough to finish, but not strong enough to create the aha.

The app asks users to complete setup. It does not yet guide them all the way to the emotional payoff: spoken context becomes local Markdown, then an agent can use it. That missing bridge is the main retention risk.

Executive Summary

COverall onboarding

Clear structure, good local-first intent, and a working first-dictation path. But it is too much setup, too little payoff, too little instrumentation, and too much friction before the user has received value.

DFunnel visibility

PostHog currently sees launch, completion, and later dictation/meeting outcomes. It cannot see the actual onboarding funnel: who saw it, clicked permissions, got stuck, closed it, waited on the model, or reached first value.

FMenu keyboard access

The immediate post-onboarding popover is built from custom mouse-only rows. Computer Use could not address the rows as controls, and the code has mouse handlers without keyboard or accessibility button semantics.

Biggest Product Problem

The app says "Welcome" and asks for permissions. It should say, in substance: "Say one sentence. We will paste it back, save Markdown locally, and show you how your agent can use it."

The current flow can end in a no-speech error, a generic menu, or a settings screen. None of those are the aha.

Biggest Measurement Problem

The event taxonomy is missing the onboarding funnel. It also has two concrete property-loss bugs: system_audio_recording_enabled likely gets dropped because the sanitizer drops keys containing audio, and dictation_completed.auto_send is sent by code but not allowlisted.

Most important recommendation: turn onboarding into a guided first capture, not a permissions checklist. The product should optimize for first useful dictation, first saved Markdown, and first agent use. Permissions are only supporting steps.

Most Obvious Things To Fix

P0

Instrument the onboarding funnel before optimizing blind.

Today, the app cannot answer the most basic onboarding questions: who saw it, who clicked a permission CTA, which permission blocked them, who closed it, who waited on the model, who started first dictation, or who got no speech.

Fix: add explicit PostHog events for every section, click, state transition, and exit. Keep properties coarse and allowlisted.

Evidence: AnalyticsEventPolicy.swift:16 only allowlists onboarding_completed for onboarding.

P0

Make the first value moment explicit.

The product promise is not permission setup. It is spoken context becoming useful. Current onboarding does not show the Markdown result, does not show where it was saved, and does not show how an agent can use it.

Fix: after first dictation, show a success panel: saved text, Markdown location, "Copy for Agent", and "Open capture folder".

P1

Replace the setup-first hero with an outcome-first hero.

Current copy says "We will get the core permissions ready." That makes users evaluate cost before value.

Fix: use a concrete one-screen promise: "Turn meetings, dictation, and audio into local Markdown your agents can read."

P1

Do not hard-block first value on Accessibility.

Accessibility is useful for hotkeys and paste-back, but it is also the scariest permission. Making it mandatory before any value is risky.

Fix: require Microphone for first dictation, but allow a degraded path: record -> show transcript -> copy manually -> save Markdown.

Evidence: FirstRunExperience.swift:38 requires Microphone and Accessibility; PermissionsOnboardingView.swift:239 refuses completion without both.

P1

Make the post-onboarding menu accessible.

The immediate post-onboarding surface should be rock solid. Right now the custom menu rows are not exposed as individual controls.

Fix: use NSButton rows or implement accessible role, title, value, help, action, focus ring, Space/Return activation, and disabled reason.

Evidence: MenuBarActionRowView.swift:244 handles mouse events directly; Computer Use saw only the popover, not rows.

P1

Move or compress observability consent.

It is transparent, but it is too much trust negotiation before the user has seen value. It also appears below the fold and can be skipped.

Fix: ask after first success, or collapse to: "Help improve Transcripted with privacy-safe diagnostics" plus two toggles in Settings.

P1

Fix analytics property loss.

system_audio_recording_enabled contains audio, and the analytics sanitizer drops any key containing audio. Separately, auto_send is sent on dictation completion but not allowlisted.

Fix: rename properties to safe enum keys or add explicit allowlist precedence before sensitive-fragment dropping.

P2

Make first no-speech a recovery flow, not a dead end.

My first Computer Use run ended in No speech detected. That is normal if someone clicks Stop quickly, but it is a bad first experience.

Fix: show "Try again", "Say: remind me to review the pricing call", and "Open Transcripted menu". Track first_capture_empty.

P2

Clarify meeting setup instead of burying it.

Meetings are core to the product, but onboarding says "Meetings later" and optional rows have no actions.

Fix: offer a branch: "I mainly want meeting notes" -> set up System Audio now -> run a meeting recording dry run.

P2

Rename the bundle id.

The bundle id is still com.justinbetker.draft. This affects TCC, defaults, logs, support screenshots, and testing.

Fix: plan a migration to a Transcripted bundle id with explicit TCC and defaults implications.

Detailed Friction Inventory

First impression and trust
  • The hero starts with permissions, not the reason the app exists.
  • "Menu bar utility" undersells the product. Transcripted is a memory layer, not merely a utility.
  • "Meetings later" is operationally true but strategically weak because meetings are one of the core use cases.
  • Accessibility copy says "For shortcuts and paste-back", but does not explicitly say what it will not do.
  • The old screenshot at docs/screenshots/onboarding.png still shows a Draft writing-profile onboarding flow. That is stale and misleading for docs or QA.
Permissions
  • Microphone and Accessibility are both mandatory before completion, even though a mic-only first capture could create value.
  • Optional permissions show status but no CTA, so users cannot set up meetings from onboarding.
  • System Audio status is cached in defaults. It can show "Ready" based on cached state until meeting start revalidates.
  • Calendar copy says it is for meeting prompts, but runtime app prompts can happen without calendar.
  • The app still uses the Draft bundle id for TCC/defaults, which can make permission instructions and support logs confusing.
Layout and hierarchy
  • The onboarding window is fixed at 620x760, non-resizable, and hides zoom.
  • The first fold cuts into the optional permissions card while the footer CTA remains visible.
  • Consent and "what happens next" are below the fold for many users.
  • Many small labels use muted text on dark/badge backgrounds. Contrast is likely under target for 10-11 point labels.
  • Cards inside cards make the lower half feel dense and repetitive.
First capture
  • The primary CTA says "Start first dictation", but there is no sample phrase or countdown.
  • The app assumes the remembered source app is a useful paste target. It may be Finder, Settings, or another non-text context.
  • If no paste target exists, the fallback tells the user to click into a text field later. That delays the aha.
  • The no-speech state can be the first post-onboarding result.
  • The success path does not teach where Markdown went or how to use it with an agent.
Post-onboarding surfaces
  • The menu popover is visually good but accessibility-poor.
  • "Connect Agent" is present, but not framed as the next step after a saved capture.
  • Settings Home is useful but too admin-heavy for first success: menu visibility toggles, ready checks, and page links compete with the first action.
  • The Agent settings page has very little explanatory copy. "Pick one" is too thin for a core setup step.
Observability and analytics
  • app_launched can be sent before the user sees analytics consent because analytics defaults on when configured.
  • onboarding_completed is not sent if the user turns analytics off before completing.
  • There is no event for onboarding_shown, so completion rate cannot be calculated reliably.
  • There is no event for permission CTA clicks or permission transitions.
  • There is no event for closing onboarding before completion.
  • There is no event for first-dictation no-speech from onboarding as a first-run funnel exit.
  • Sentry is strong on privacy but missing onboarding-specific failure context.

PostHog Plan

Principle: do not use broad autocapture for this native macOS onboarding. Use explicit event calls with stable action ids and coarse properties. The app captures sensitive local work context, and the current transport is a custom direct /capture/ client, not the PostHog SDK.

Current State

  • PostHog config is read from Info.plist, environment, or local overrides in AnalyticsReporter.swift.
  • Transport sends direct capture requests and adds distinct_id, app_version, os_major, and session_id.
  • Allowed events live in AnalyticsEventPolicy.swift.
  • Current onboarding event: onboarding_completed only.
  • Sanitizer drops sensitive property names and redacts sensitive values.

Funnel Definitions

  • Dictation activation: app_launched -> onboarding_shown -> onboarding_completed -> dictation_requested -> dictation_listening_started -> first_capture_saved.
  • Permission success: onboarding_shown -> onboarding_permission_cta_clicked -> onboarding_permission_status_changed(to_status=granted) -> onboarding_completed, broken down by permission_kind.
  • Model readiness: onboarding_shown -> onboarding_model_state_changed(to_state=ready) -> onboarding_primary_cta_clicked -> dictation_listening_started.
  • Meeting setup: onboarding_shown -> meeting_setup_cta_clicked -> meeting_audio_permission_result -> meeting_recording_started -> meeting_transcript_saved.
  • Agent aha: first_capture_saved -> agent_setup_cta_shown -> agent_setup_cta_clicked -> agent_setup_completed.

Privacy Rules For PostHog

  • Never send transcript text, audio references, meeting titles, speaker names, emails, source app names, bundle ids, raw URLs, file paths, or raw error messages.
  • Prefer enums and buckets: permission_kind=accessibility, duration_bucket=10_29s, failure_kind=no_speech.
  • Use allowlist-first sanitization. Current sensitive-fragment dropping is good, but it accidentally drops legitimate coarse keys like system_audio_recording_enabled.
  • Do not use broad autocapture for native app setup. PostHog autocapture can collect many interaction types depending on SDK and config. This app should use explicit actions only.
  • Session replay should be opt-in only, sampled, and heavily masked. For this app, explicit events are safer and probably enough.

PostHog Product Features To Use

  • Funnels: use for step-by-step drop-off and time-to-convert analysis.
  • Cohorts: use to isolate stuck users and compare return behavior.
  • Surveys: after failure or first success, ask one lightweight question like "What nearly stopped you from finishing setup?"
  • Feature flags: test consent timing, Microphone-only path, meeting-first branch, and first-capture success panel.

Sentry Plan

Current Sentry posture is mostly right. Sentry is for crashes and reliability failures, not onboarding clickstream. Keep automatic breadcrumbs, screenshots, view hierarchy, request data, and PII off unless there is a very deliberate privacy review.

Current State

  • CrashReporter.swift sets sendDefaultPii=false, disables network breadcrumbs, sets maxBreadcrumbs=0, blocks screenshots/view hierarchy, and sanitizes before send.
  • EventReporter.swift forwards only .error events that match SentryEventPolicy.
  • SentryEventPolicy.swift covers model/audio/hotkey/paste failures, not onboarding-specific reliability failures.

What To Add

onboarding.model_download_failed Runtime model download fails during onboarding. model_kind, download_source, failure_kind No URLs, no file paths.

meeting.system_audio_permission_request_failed ScreenCaptureKit permission probe fails in a non-user-cancel way. permission_check, failure_kind, macos_major Useful because meeting setup is a high-value funnel.
