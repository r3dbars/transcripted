Transcripted Health Brief · April 15, 2026

Used, growing, and still tripping on launch.

In the last 7 days through April 15, 2026, Transcripted showed real usage and rising public interest, but the shipped build 1.0.7 is still taking a real startup/audio hang. The repo is already at 1.0.8, so the biggest gap right now is not insight. It is getting the fixes into users’ hands.

Sentry: Real Vs Noise

Real bug

APPLE-MACOS-5 · launch/audio hang

This is the one to care about first. It looks like launch-time audio initialization is still touching the wrong path too early on the public build.

  • 14 production app hangs in the last 7 days, with the latest seen on April 15, 2026.
  • The stack lands in AVAudioEngine.inputNode during launch.
  • PR #318 matches this path almost perfectly, but users are still mostly on 1.0.7.
Watch

APPLE-MACOS-H · backend/download turbulence

This looks real, but not like the core blocker. It is a short burst of infrastructure pain, not the main recurring product failure.

  • 8 production HTTP 503/504 events on April 14, 2026, all on 1.0.7.
  • The frames are system-only network/download paths, not the same shape as the launch hang.
Noise

Do not let these steal attention

Sentry has a little honest noise in it right now, and it is worth ignoring on purpose.

  • APPLE-MACOS-2 is the intentional sentry_test_event from Settings.
  • APPLE-MACOS-1 is a Sentry dashboard/sample JavaScript issue, not a Transcripted Mac app failure.

What To Test

Scenario Why Pass condition
Cold launch on the build after #318 The top Sentry issue is a launch-time audio hang. App opens cleanly and does not touch launch-time audio capture until recording actually starts.
Deny microphone, then recover through Settings mic_not_authorized showed up on 1.0.6 and the UX copy was just tightened. The UI sends people to the right macOS pane and recovery feels obvious, not cryptic.
Short meeting and model-download failure handling Meeting failures include recording_too_short, and there was a smaller burst of 503/504 download pain. The app fails gracefully with a clear reason and a clean next step, not a generic dead end.
Code paths to watch

Startup, capture, and attribution boundaries

If the next release moves the Sentry picture, these are the seams most likely to explain it.

  • AppDelegate.applicationDidFinishLaunching and early meeting setup.
  • Audio, AVAudioEngine.inputNode, and system-audio device listener paths.
  • MeetingFailureKind plus trigger propagation into save/fail analytics after #323.

What To Fix

1. Ship

Get users off 1.0.7 fast

The repo already has fresh reliability work merged on April 15, 2026. The biggest win is to publish that work so the shipped build is not still the one generating the hang.

2. Cover

Treat short and failed captures like product states

recording_too_short, permission misses, and transient download failures should feel handled, explained, and recoverable instead of looking like mysterious product breakage.

3. Triage

Clean the signal before the next review

Deduplicate the stale nightly automation issues, keep test events out of the way, and let the new meeting trigger attribution build a cleaner next read.

Bottom Line

Fix now

Ship past the hang

Transcripted has enough real usage now that the launch/audio hang is holding back a product people are actually trying to use.

Fix next

Reduce first-minute friction

The next biggest drag is setup and failure handling: permissions, short captures, and backend turbulence need cleaner recovery.

Set up next

Measure the site and the meeting funnel

GitHub interest is rising faster than downloads, and website analytics are still missing, so the growth story is still blurrier than it needs to be.
