Sentry: Real Vs Noise

There are four unresolved issues, but only one currently looks like user-facing Transcripted product pain.

Real Bug

APPLE-MACOS-3

Parakeet transcription failed. This is the only issue that clearly belongs in the current fix queue.

  • Scope: 4 events, 1 user, all in production on transcripted@1.0.3.
  • Pattern: Sentry captured “Invalid audio data provided. Must be at least 1 second of 16kHz audio.”
  • Interpretation: This looks like the shipped build hit Parakeet with sub-threshold audio before the new guard landed.
  • Main code path: ParakeetEngine now skips short dictation clips at 868-881 and short meeting segments at 949-959.
Watch

APPLE-MACOS-4

App hang for at least 2000 ms. Important enough to watch, not strong enough yet to drive immediate code changes.

  • Scope: 1 event, 0 impacted users, first and last seen April 12, 2026.
  • Signal quality: One isolated hang with no clear first-party culprit.
  • Working read: Keep it on the watchlist and only escalate if it repeats.
Noise

APPLE-MACOS-2

Sentry test event. This is expected verification traffic from Transcripted Settings.

  • Scope: 2 events, 1 user, tagged source=manual_test.
  • Meaning: Good proof that Sentry wiring works.
  • Action: Ignore or resolve it so the issue board stays usable.
Noise

APPLE-MACOS-1

Sentry dashboard JavaScript error. This is not a Transcripted macOS app failure.

  • Scope: 1 event, culprit in ../../sentry/scripts/views.js.

  • Action: Ignore it and do not spend engineering time on it.

What To Test

These are the tests worth running next if the goal is to turn the live Sentry picture into confidence instead of guesses.

Scenario Why Pass Condition
Dictation under 1 second This directly targets APPLE-MACOS-3. Transcripted quietly skips transcription, inserts nothing, and does not emit parakeet.transcription_failed.
Boundary dictation around 1 second Confirms the new threshold behaves sanely at the edge. 0.9s gets skipped cleanly, while 1.0s-1.2s either transcribes or returns empty without Sentry noise.
Meeting transcription with short speaker turns Main already guards short meeting segments too. Short segments are dropped cleanly and the overall meeting transcript still saves without a failure surfacing to the user.
Launch and settings modal flows This is the cheapest smoke pass for the one app-hang event. No repeated hangs while opening settings, permission prompts, or other blocking UI flows.
Sentry test button Keeps observability honest without mistaking it for product pain. The verification event lands once, is obviously tagged as test traffic, and can be ignored cleanly in triage.
Code Paths To Watch

Where The Current Guard Lives

The short-audio protection is already in the codebase. The question is shipping it and validating behavior, not inventing a new approach.

  • ParakeetEngine: dictation guard at 868-881, failure emit path at 912-920.
  • ParakeetEngine: meeting segment guard at 949-959.
  • TranscriptedConstants: minimum threshold defined at 39-48.
  • TranscriptedConstantsTests: constant coverage exists, but behavior coverage is still thin.
  • SentryEventPolicy: parakeet.transcription_failed is still allowlisted, so noisy regressions will show up fast if this path remains reachable.

What To Fix

This is the actual order of operations if the goal is better product health, not just a cleaner dashboard.

1. Ship

Release the short-audio guard

The highest leverage fix is to ship a build newer than 1.0.3 so users actually get the guard that now exists on main.

  • Current shipped issue is on the live release, not on current main.
  • If you want users to discover it in-app, the next release also needs appcast updates.
2. Cover

Add behavior tests, not just threshold tests

The repo proves the sample threshold constant, but not the user-facing behavior around skipped short audio.

  • Add a focused test for “short audio returns nil or empty and does not emit transcription_failed.”
  • Add one meeting-path test to verify short segments are skipped without breaking transcript save.
3. Triage

Clean the Sentry board

Two of the four unresolved issues are not product work and should stop stealing attention.

  • Ignore or resolve APPLE-MACOS-2 and APPLE-MACOS-1.
  • Leave APPLE-MACOS-4 open as a watch item unless it repeats.
4. Instrument

Only deepen hang work if the signal repeats

The app-hang issue is too sparse to justify a speculative fix right now.

  • If it comes back, add targeted breadcrumbs around launch-time alerts and settings modal flows.
  • Until then, keep this as a smoke-test item, not a blocker.
