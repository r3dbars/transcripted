# Speech Directory

## What This Does

`Sources/Speech/` owns the app's live dictation speech path.

## Key Files

- `ParakeetEngine.swift` — app-owned Parakeet STT engine, recording control, final dictation transcription, permission-aware input-readiness checks, short-audio gating, live level metering, and sanitized failure reporting for model init errors. Device-change recovery, model lifecycle, system-input restore/reconciliation, zombie-engine recovery, and shared-meeting-mic bridging are split into the extension files below — ParakeetEngine remains the public-API owner and `@MainActor` home for that state; the split files are internal collaborator extensions.
- `ParakeetDeviceRecovery.swift` — `ParakeetEngine` extension: device-change detection (CoreAudio default-input listener, `AVAudioEngineConfigurationChange` observer) and the `attemptDeviceRecovery` / `scheduleConfigRecoveryTimeout` executor that rewarms the audio graph after a route change. The pure decision tables it consults (`ParakeetDeviceRecoveryReadinessPolicy`, `ParakeetDeviceRecoveryFailurePolicy`, `ParakeetDeviceRecoveryTimeoutPolicy`) live in `ParakeetStartRecordingFailurePolicy.swift`, not here.
- `ParakeetModelLifecycle.swift` — `ParakeetEngine` extension: model load/download/warmup/teardown paths (`initialize`, `performInitialize`, `prefetchModelFilesIfNeeded`, `cancelModelWork`, `teardownModel`)
- `ParakeetModelState.swift` — shared model-lifecycle enum (`notLoaded`/`downloading`/`cached`/`loading`/`ready`/`failed`) that `ParakeetModelLifecycle` and the warmup/first-run policy files consume directly instead of keeping per-surface mirror enums in sync by hand
- `ParakeetSystemInputCoordination.swift` — `ParakeetEngine` extension: the owner-bound pending-restore handoff, bounded-timeout CoreAudio writes through the replaceable system-input work coordinator, and the reconciliation queue that converges late (timed-out) HAL completions back onto current MainActor intent. The 2026-08-24 Bluetooth audit removed the per-dictation Mac-wide default-input override, so nothing populates `pendingSystemInputRestore` anymore — every restore call site is a deliberate no-op through its `take(ownedBy:)` guard, retained as the owner-lease contract for any future temporary override
- `ParakeetSharedMeetingMicBridge.swift` — `ParakeetEngine` extension: borrowed-mic dictation while a meeting owns the microphone — start/finish of borrowed-mic recording, relayed PCM buffer and level intake, resuming regular mic capture when the meeting ends first, and stale-claim resolution/finalization (see `SharedMeetingMicClaim.swift` for the handshake rationale)
- `SharedMeetingMicClaim.swift` — pure claim/staleness types for the meeting-mic sharing handshake: `SharedMeetingMicClaim` carries a liveness probe from `MeetingSessionController` into `ParakeetEngine` so a claim can be told apart from a stale one left behind by an unexpected meeting teardown
- `SharedMeetingMicRecorder.swift` — thread-safe buffer for dictation samples borrowed from an active meeting's mic tap; `MeetingCaptureBridge` delivers PCM on its relay queue while `begin`/`append`/`finish`/`cancel` stay safe to call from `@MainActor` via an internal lock
- `ParakeetZombieEngineRecovery.swift` — `ParakeetEngine` extension: the startup audio watchdog that detects zombie engines (running but no usable signal after sleep/wake) and the separate generation-gated recovery task that replaces the stale `AVAudioEngine` through a bounded reset and retries once; the audio-graph/queue owner-token types those paths consult live in `ParakeetAudioGraphOwnership.swift`, not here
- `ParakeetSystemWakePolicy.swift` — pure decision for how `ParakeetEngine`'s system-wake handler reacts: skip tearing down the dormant audio graph while shared-meeting-mic dictation owns it, otherwise tear it down and mark an in-progress recording interrupted
- `ParakeetAudioDeviceLookup.swift` — CoreAudio default-input lookup and dictation input selection descriptors used before Parakeet starts recording
- `ParakeetAudioEngineSupport.swift` — support types for Parakeet engine startup snapshots, retired-engine retention, and default-input listener teardown
- `ParakeetAudioGraphOwnership.swift` — the generation-gated owner-token types (`ParakeetAudioGraphOwnerToken`, `ParakeetAudioEngineQueueOwnerToken`, `ParakeetAudioStartAdmissionState`), timed-work lease bookkeeping (`ParakeetTimedAudioEngineWorkOwnership`), start-cancellation state, and the replaceable system-input work coordinator that `ParakeetEngine` constructs and consults on every start/stop path
- `ParakeetTimedAudioEngineWorkLimiter.swift` — process-wide admission circuit for timed `AVAudioEngine` work; each acquired `Lease` holds its slot until the underlying CoreAudio call actually returns, even past its own timeout, so a permanently blocked call cannot let replacement workers pile up unbounded
- `WhisperEngine.swift` — app-owned WhisperKit STT engine used when advanced users select a Whisper model
- `DictationAudioLevelMeter.swift` — normalizes live PCM buffers into a 0...1 level used by the dictation waveform UI
- `DictationAudioRecovery.swift` — analyzes recorded dictation audio for usable speech signal and extracts focused, gain-normalized retry segments when an initial transcription attempt returns empty
- `DictationInputDeviceSelectionPolicy.swift` — follows the macOS input for normal dictation; the explicit faster-Bluetooth preference may recommend a built-in mic to avoid playback downgrades
- `PersistentDictationInputController.swift` — owns the explicit faster-Bluetooth-dictation preference at runtime: keeps the preferred non-Bluetooth system input selected, follows device reconnects, and restores prior input ownership across clean or unclean exits. Startup, reconnect, preference changes, and clean-exit restoration wait for external microphone capture to be idle; unknown process-activity reads defer writes, and skipped exit restoration keeps its durable recovery marker. Writes the system default input only through `DefaultInputDeviceMonitor.shared.setDefaultInputDevice(_:)` so its own writes are self-suppressed centrally.
- `DefaultInputDeviceMonitor.swift` — the single, `@MainActor` `AudioObjectAddPropertyListenerBlock` registration for `kAudioHardwarePropertyDefaultInputDevice`, shared by `PersistentDictationInputController`, `ParakeetEngine`/`ParakeetDeviceRecovery`, and `Sources/Meeting/MicActivityMonitor.swift` (previously three independent registrations with no ordering guarantee). Ordinary external changes fan out immediately without a redundant HAL read. A possible self-write echo uses a bounded, off-main ID lookup; subscribers receive each retained event in registration order with the centrally classified `isSelfWrite` flag. No observer is globally suppressed; each decides whether to react. The one-use expected-ID/deadline token is captured at callback admission, so a late A result cannot consume a newer B write marker; classification uses callback time, not delayed HAL-completion time. A burst while an echo is in flight retains at most the first event, earliest pending write echo, and latest remaining event. Do not register a fourth direct listener on this property — subscribe here instead.
- `DefaultInputDeviceMonitorSupport.swift` — testable types backing `DefaultInputDeviceMonitor`: the `DefaultInputDeviceSubscribing` protocol `MicActivityMonitor` depends on instead of the concrete singleton, the order-preserving observer registry and self-write tracker, and the bounded notification mailbox/timeout dispatcher. The monitor reuses its one process-lifetime coordinator across stop/start, so a blocked lookup can retain at most two timed-out worker threads; unknown results still notify observers conservatively as external changes, while late and closed-monitor results are discarded.
- `DictationReadinessWaitPolicy.swift` — tiny policy that decides whether dictation should keep waiting for recovery, refresh input readiness, or start recording immediately
- `DictationStartReadiness.swift` — pure policy that decides, from whether Transcripted was the active app when the start was requested, how the start labels itself in diagnostics and whether it may escalate to the foreground-activation handshake. It deliberately carries no CoreAudio timeouts and no wait budget — see the header comment for why an earlier revision that did was wrong, and for what issue #1743 established versus what is still inference.
- `DictationProcessActivity.swift` — reference-counted `ProcessInfo.beginActivity` App Nap suppression held for the length of a dictation session. `DictationSessionController` balances it on `isDictating` transitions so every session-ending path releases it.
- `DictationSession.swift` — `@MainActor` engine-facing dictation orchestrator extracted out of `DictationSessionController`: owns the recovery wait-loop state machine (`waitForEngineAndStart`, merging the former `.startRecoveryRecording`/`.startRecording` duplicate paths), the model-warmup wait loop (`waitForModelAndStart`), `startDictationAudioRecording`, and the small STTRouter-touching cleanup/cancel helpers. Talks to `STTRouter` directly and reports back through outcome enums and injected status closures instead of touching overlay types, so `DictationSessionController` stays the only place that turns those into panel presentation.
- `DictationSessionTypes.swift` — `DictationSession`'s class declaration plus its pure, `TranscriptedAppState`-free nested types (`WaitStatus`, `StartOutcome`, `StartPathDecision`, ...); split out so `run-tests.sh` can compile and fast-test them without pulling in `TranscriptedAppState`'s whole-app dependency graph, the same constraint that keeps `DictationSessionController` itself out of the fast-test source list. `DictationSession` deliberately does not publish its own lifecycle/state enum — `DictationSessionController.isDictating` stays the single source of truth; see the NOTE at the top of this file for why an earlier `@Published var state` was removed.
- `ParakeetModelInitDiagnostics.swift` — builds safe diagnostic context for model-initialization failures without leaking transcript or user-content data
- `ParakeetPrewarmPolicy.swift` — central policy for deciding whether speech-engine input-readiness checks should proceed or be skipped based on microphone authorization state
- `ParakeetRecoveryState.swift` — pure-logic state machine for device-change recovery: generation counter (so stale recovery tasks can bail) and readiness flags (`isRecovering`, `inputFormatReady`) that the dictation overlay waits on instead of racing
- `ParakeetShortAudioGate.swift` — central policy for deciding when very short recordings should be dropped, surfaced as intentional empty results, or still transcribed
- `ParakeetStartRecordingFailurePolicy.swift` — central recovery policy for invalid-format and audio-engine-start failures during recording startup
- `RecordedAudioTimeline.swift` — in-memory segmented audio buffer used when recorded audio needs to be preserved across interruptions or recovery handoffs
- `TranscriptionModelWarmupOwnership.swift` — balanced, generation-safe ownership state for disposable background model warmup versus active dictation/meeting/import use; shared runtimes resolve concurrent foreground work onto one concrete model
- `STTRouter.swift` — small main-actor wrapper used by the rest of the app

## Current Notes

- This directory powers dictation.
- `ParakeetEngine` consults `ParakeetPrewarmPolicy` before checking microphone input readiness. Idle readiness checks must not leave `AVAudioEngine` running, because that keeps the macOS microphone indicator active.
- `ParakeetEngine` consults `ParakeetShortAudioGate` before spending work on extremely short clips, so short-tap behavior changes belong here rather than in UI controllers.
- `ParakeetEngine` mirrors `ParakeetRecoveryState` flags into `@Published var isRecovering` and `@Published var inputFormatReady` (forwarded through `STTRouter`). `DictationSession.waitForEngineAndStart` distinguishes recovery, readiness refresh, and safe start. Startup resolves the tap format from the live node after applying voice processing: raw input uses the hardware input format; active VPIO uses its processed output format. Do not use `format: nil` to assume conversion of AirPods 24kHz hardware to a stale 48kHz output bus: a physical macOS 27 reproduction failed with `-10868`. Each retained buffer still keeps its delivered sample rate, and final inference/persistence resample each segment independently. Policy tests are not physical AirPods proof.
- `ParakeetEngine` consults `DictationInputDeviceSelectionPolicy` through `ParakeetAudioDeviceLookup` before recording to follow the selected macOS input, including AirPods. Only the opt-in `PersistentDictationInputController` requests a built-in recommendation for faster Bluetooth starts. Every selection, including following a new default, must match the actual AUHAL binding before readiness is published; binding failures use bounded route settling instead of graph churn.
- Dictation must NEVER write the Mac-wide default input device (kAudioHardwarePropertyDefaultInputDevice) per session — microphone selection binds only the app's own AUHAL via `applyPreferredDictationInputDevice`. The 2026-08-24 Bluetooth audit found the old per-session write/restore cycle caused the AirPods route flip-flop, a ~470ms-vs-83ms start tax, audible playback perturbation, and (being untracked) silently killed `PersistentDictationInputController`'s ownership. `Tests/BluetoothRouteContractTests.swift` pins the negative invariant. The only legitimate Mac-wide input writes are `PersistentDictationInputController`'s, which go through `DefaultInputDeviceMonitor.shared.setDefaultInputDevice(_:)` for self-write suppression. Idle prewarm now always performs the real AUHAL bind + format readiness check (no Bluetooth-fallback deferral), so Bluetooth-route dictation starts from a genuinely settled graph; prewarm still must not leave `AVAudioEngine` running.
- `ParakeetEngine` consults `ParakeetStartRecordingFailurePolicy` when startup fails so format-reset, engine rebuild, and prewarm-retry behavior stay consistent across direct starts and recovery attempts.
- Recovery retains recording intent across notification bursts until the current generation finishes. Terminal interruption clears restart intent before publication but preserves captured audio for explicit recovery; retained audio alone must never restart capture or carry into a fresh dictation.
- Route-change analytics are committed only after the config-change debounce resolves to a new categorical route. Notification churn and A -> B -> A oscillation stay quiet. Input-device lookups use one latest-wins mailbox, and idle route changes only mark readiness stale; native graph recovery runs when a recording is active or when the user next starts dictation.
- Zombie-engine recovery owns a separate generation-gated task, replaces the stale `AVAudioEngine` through a timed reset, and retries once. Do not fold that task back into the startup watchdog or reuse the detected zombie graph.
- Timed `AVAudioEngine` work has a four-worker process-wide circuit. Each queued block keeps its lease until it actually returns, even after its caller times out, so permanently blocked CoreAudio work cannot create a fifth worker/graph. Retired native graphs also have a four-entry delayed-release cap while late callbacks drain; once either circuit is full, Transcripted fails closed instead of replacing again.
- Timed-out system-input CoreAudio writes have a two-worker circuit breaker. A first blocked queue may be replaced once; after two still-running operations, later route work fails immediately until a timed-out worker returns instead of accumulating blocked queues and threads.
- Default-input and audio-engine configuration notifications must dispatch recovery even when a CoreAudio route-selection lookup times out. Keep both notification lookups off the main actor and behind separate two-worker bounded circuits, and pass an explicit unknown route to recovery rather than retrying an unbounded detached HAL read. Unknown input is not proof of microphone readiness.
- `ParakeetEngine` stays `@MainActor` for app state, published UI state, and event reporting, but all `AVAudioEngine` graph work runs through its private serial audio-engine queue. Keep recording start/stop/readiness APIs async so callers do not block the main actor while CoreAudio settles, starts, stops, or rebuilds.
- The early-release error has exactly one producer: `DictationSessionController.cancelPendingDictationStartAfterEarlyRelease`, reached only when the user's own hotkey ends a session whose microphone start has not landed yet. **Its wording is no longer fixed.** `DictationEarlyReleasePresentationPolicy` picks it from `shortcut_mode` and the elapsed milliseconds: a Push to Talk release under 250ms was a tapped key, not a slow microphone, and gets "Hold the key while you speak" — see #1743, where blaming the mic cost the reporter five days of swapping hardware. Everything else keeps "Mic wasn't ready yet. Nothing was recorded." Push-to-talk release and the hands-free second press (the default mode) both arrive as `trigger: physical_key`, so the trigger alone does not tell them apart — read `shortcut_mode` on the `dictation_cancelled_before_microphone_ready` event. A start that exhausts `dictationRecoveryBudget` surfaces `microphoneTimeoutMessage` instead, which is a different bug with a different message. Do not conflate them. That event is recorded at `.error` and allowlisted for Sentry, and the level is load-bearing: `EventReporter` forwards off-device only at `.error`, so dropping it back to `.info` would silently stop it reaching Sentry with no other symptom. Sentry receives the trigger, shortcut mode, pending stage, whether the app was frontmost, and two `latencyBucket` durations — never the raw milliseconds, which stay in the local log for a reporter to grep. Note the key is `start_plan`, not `start_profile`: the shared sensitive-key fragment list drops any key containing `file`, and `profile` does. A tag key that is allowlisted and then silently dropped by the sanitizer looks like working code from both sides, so `Tests/SentryEventPolicyTests.swift` now checks the two lists agree.
- A dictation start requested while Transcripted is NOT the active app may be slower than one from the menu — the suspected mechanism is App Nap demoting the audio-engine queue, since a menubar accessory app that is not frontmost is a candidate for it. `DictationSessionController.startDictation` therefore takes the `DictationProcessActivity` assertion and picks a `DictationStartReadinessProfile` BEFORE any audio work. Treat that as a hypothesis under test, not a diagnosis: no stage has been measured running slow on the affected machine (issue #1743). `pending_stage` and `stage_pending_for_ms` on the cancel event are what would settle it. Recovering *after* a failed background start was tried in PR #1744 and was not enough, so do not move the preparation back after the first microphone open.
- Do NOT widen the CoreAudio fences per start by setting "fence in flight" properties on `ParakeetEngine`. An earlier revision of the #1743 work did, and it was wrong twice: `ParakeetEngine` is `@MainActor` and a start suspends many times, so prewarm, `ParakeetDeviceRecovery` and `ParakeetZombieEngineRecovery` read the widened values whenever they interleave with a suspended start; and the recovery restarts (`ParakeetDeviceRecovery`, `ParakeetZombieEngineRecovery`, `ParakeetSharedMeetingMicBridge`) call `startRecording()` with the default, so later attempts silently dropped back to the foreground values. A per-start fence has to be threaded as a parameter through `audioInputSnapshot` and `runTimedAudioEngineWork`, and is worth doing only once a measurement says a stage actually needs it.
- `NSApp.isActive` read in `startDictation` means "was Transcripted frontmost the instant the start was requested", not "stays frontmost while the microphone opens". The menu path calls `sourceApp?.activate` on the line before, and AppKit activation is asynchronous, so a menu start samples as foreground and then hands focus away mid-start. That is intended: the sample stands in for "the process was in use a moment ago", which is what decides whether App Nap has had a chance to demote it.
- `ParakeetEngine` reports model-init failures with `ParakeetModelInitDiagnostics.failureContext(...)`, which keeps diagnostics useful for packaging/download/debugging issues without shipping raw transcript or device content.
- `scripts/ops/dictation-stop-autoeval.sh --encoder-compute cpu-and-gpu|all` is the local-only encoder compute comparison. Production keeps FluidAudio's default unless that benchmark process sets `TRANSCRIPTED_PARAKEET_ENCODER_COMPUTE_UNITS`.
- Dictation intentionally exposes only final transcription. The abandoned provisional-text/EOU path was removed rather than kept behind a false feature flag. A future live dictation experience must add a real streaming engine and end-to-end tests instead of reviving dormant audio-tap branches.
- `DictationAudioLevelMeter` converts live audio buffers into normalized meter levels using `TranscriptedConstants` floor and ceiling thresholds. Keep waveform calibration changes here instead of burying them in overlay code.
- `DictationAudioRecovery` analyzes buffered audio for usable speech signal (peak, RMS, active ratio) and can produce a focused, gain-normalized retry segment. `ParakeetEngine` uses it to retry transcription when an initial attempt returns empty rather than silently dropping audio that contained real speech.
- The meeting pipeline reuses the same app-owned `STTRouter` through `Sources/Meeting/MeetingSTTAdapter.swift`.
- Do not assume a separate local-LLM drafting path exists in this tree.

## Verification

After changing speech code:

```bash
bash build.sh --no-open
bash run-tests.sh
```

Manual checks:

- dictation can start and stop cleanly
- very short recordings follow the expected drop / empty-result / transcribe behavior
- final dictation text appears after stop/transcribe; provisional live text is not shown
- device changes do not leave the app stuck or force a Bluetooth headset mic when a safer built-in fallback exists
- wake / resume does not strand buffered audio or leave recovery state hanging
