# Speech Directory

## What This Does

`Sources/Speech/` owns the app's live dictation speech path.

## Module

`Speech` in `.agents/modules.json`.

- **Owns:** dictation STT and the dictation mic engine: `STTRouter`, `ParakeetEngine` and its extensions, the persistent dictation input, device monitoring, the shared meeting mic, and `DictationSession`.
- **Public surface:** `STTRouter`, `ParakeetEngine`, `PersistentDictationInputController`, `DefaultInputDeviceMonitor`, `SharedMeetingMic*`, `DictationSession` and its types, the dictation start/stop policies in `DictationRecordingStartOverlayPolicy.swift`, and `DictationTrigger` / `DictationHotkeyRouter`.
- **May depend on:** Support, Observability, Core `core-vocab`, and Core `mic-primitives` (`PinnedMicrophoneCapture*`, `MicrophoneDownmix`, `MacLidState`, `AudioTapInstallGuard`, `AudioInputTapTeardownPolicy`, `ModelDownloadService`).
- **Grandfathered crossings:** `DictationSession.swift` takes `TranscriptedAppState`; `ParakeetASRInference.swift` and `STTRouter.swift` name Core's `TimedTranscriptToken`. Fixes: inject narrow dependencies, and add the token type to a Core tier if that's the right edge.
- **Entry points:** `STTRouter.transcribe`, `ParakeetEngine` recording start / stop, `DictationSession`.
- **Tests:** `bash run-tests.sh --filter Parakeet`, `--filter STTRouter`, `--filter Dictation`; the real proof is `bash check.sh hardware`.
- **Rules:** every PR touching this module states what happens with a Bluetooth headset as the default input, even when the answer is "unchanged, moved only". See "Current Notes" below.

## Key Files

- `ParakeetEngine.swift` — the engine's core: stored state, the native `AVAudioEngine` teardown calls and `ParakeetAVAudioEngineGraphDriver`, observers, cleanup and `deinit`. The engine and its queue live in `audioGraph` (`ParakeetAudioGraph.swift`); `audioEngine`, `audioGraphGeneration` and the owner-token helpers forward to it. `ParakeetEngine` stays the public-API owner and `@MainActor` home for its state; every other `Parakeet*.swift` file below is an internal collaborator extension. The dictation path is split into:
  - `ParakeetInputReadiness.swift` — prewarm and input-format readiness, published recovery state
  - `ParakeetInputRoute.swift` — input device selection and the route/format context used for diagnostics and analytics (Bluetooth route classification included)
  - `ParakeetAudioTap.swift` — installs the dictation input tap and starts the engine, applies the voice-processing preference, extracts mono samples (the tap closure lives here)
  - `ParakeetRecordingStart.swift` — `startRecording`, the audio watchdog, start-failure handling and call-app mic sharing; it touches the engine and `inputNode`, so it's AirPods-sensitive
  - `ParakeetRecordingTeardown.swift` — stop, cancel, failed-start reset, wake handling, idle hardware release
  - `ParakeetDictationTranscription.swift` — the recorded-sample timeline, draining and final dictation transcription, stopped-audio recovery
  - `ParakeetASRInference.swift` — the Parakeet ASR call, with token times
  Device-change recovery, model lifecycle, zombie-engine recovery, and shared-meeting-mic bridging are in the extension files below.
- `ParakeetDeviceRecovery.swift` — `ParakeetEngine` extension: device-change detection (CoreAudio default-input listener, `AVAudioEngineConfigurationChange` observer) and `attemptDeviceRecovery` / `scheduleConfigRecoveryTimeout`, which hand the real CoreAudio steps to `ParakeetDeviceRecoverySequence` to rewarm the audio graph after a route change. The pure decision tables it consults (`ParakeetDeviceRecoveryReadinessPolicy`, `ParakeetDeviceRecoveryFailurePolicy`, `ParakeetDeviceRecoveryTimeoutPolicy`) live in `ParakeetStartRecordingFailurePolicy.swift`, not here.
- `ParakeetConfigChangeRecoveryHost.swift` — `ParakeetEngine`'s `ParakeetConfigChangeRecoveryHost` conformance (begin/cancel recovery bookkeeping), split out of `ParakeetDeviceRecovery.swift`.
- `ParakeetModelLifecycle.swift` — `ParakeetEngine` extension: model load/download/warmup/teardown paths (`initialize`, `performInitialize`, `prefetchModelFilesIfNeeded`, `cancelModelWork`, `teardownModel`). Local-install-only variants (the experimental Parakeet Ultra) load through `ParakeetLocalModelLoader.swift`, never through `AsrModels.load`/`download`: FluidAudio's failed-load recovery deletes the folder and downloads stock v3 into it. A missing or broken install fails as `ParakeetLocalModelError` (local warning, not Sentry) and is never deleted; the install marker is re-checked after the load (`ParakeetLocalModelPolicy` in `ParakeetModelInitDiagnostics.swift`)
- `ParakeetModelState.swift` — shared model-lifecycle enum (`notLoaded`/`downloading`/`cached`/`loading`/`ready`/`failed`) that `ParakeetModelLifecycle` and the warmup/first-run policy files consume directly instead of keeping per-surface mirror enums in sync by hand
- `ParakeetAudioGraph.swift` — the audio-graph seam: the current engine, its serial queue, the owner generation, and every teardown and replacement (tap removal, stop, idle release, failed-start reset, rebuild, abandon, zombie replacement, cancellation of blocked work). Native calls go through `ParakeetAudioGraphDriver` (production: `ParakeetAVAudioEngineGraphDriver`); engine side effects through `ParakeetAudioGraphHost`. Each operation captures an owner before it suspends and checks it after, so late work never touches a successor. Fast-tested with a fake driver in `Tests/ParakeetAudioGraphTests.swift`
- `ParakeetDeviceRecoverySequence.swift` — the device-change recovery and timeout orderings, driven by closures: only the current generation releases latched recording intent, AUHAL binding errors wait and poll until superseded, a cancelled or stale snapshot never commits its sample rate, and a failure or timeout rechecks ownership after publishing the interruption before it rebuilds. Fast-tested with a recording fake in `Tests/ParakeetDeviceRecoverySequenceTests.swift`
- `ParakeetAudioGraphSequences.swift` — the orderings the engine runs on that graph: the user stop (`ParakeetStopRecordingSequence`), route-change teardown (`ParakeetConfigChangeTeardown`), the route-recovery restart loop, the recovery snapshot lease, and snapshot selection admission. ParakeetEngine supplies the real steps through small host protocols
- `ParakeetSharedMeetingMicBridge.swift` — `ParakeetEngine` extension: borrowed-mic dictation while a meeting owns the microphone — start/finish of borrowed-mic recording, relayed PCM buffer and level intake, resuming regular mic capture when the meeting ends first, and stale-claim resolution/finalization (see `SharedMeetingMicClaim.swift` for the handshake rationale)
- `ParakeetPinnedMicrophone.swift` — `ParakeetEngine` extension: dictation's pinned-device mic path behind `PinnedMicrophoneCapturePreferences` (on by default). When on and Apple voice processing is not requested, dictation records the selected input through Core's `PinnedMicrophoneCapture` (a Core Audio IOProc) and never creates the engine's input node, so a Bluetooth headset that is the macOS default input is never pulled into call mode. The one Settings "Microphone" choice (`MicrophoneChoicePreferences`) decides the mic. A Bluetooth headset that is the macOS input is skipped unless it is "Same as macOS Sound settings"; the meetings-only "use the macOS input" setting (`MeetingMicrophonePreferences.usesSystemInput()`) never applies here, because following it put dictation back on the headset mic. When the headset is skipped, `PinnedDictationInputPolicy` prefers the picked mic, then the built-in mic, then a wired or USB mic on Macs with no built-in one; a picked mic also wins over a safe macOS input (`chosenInputAlwaysWins`, reason `userChosenInput`). The recorder is used when that choice skips a Bluetooth headset that is the macOS input, records a picked mic the engine can't reach, or records a plain built-in or wired mic, because it delivers first audio about 2-3x sooner than the engine (`PinnedDictationInputPolicy.recorderIsNeeded`), unless that mic's speed-only takes kept coming out empty (`PinnedDictationSpeedPath`); a Bluetooth headset that is itself the recorded mic, and aggregate, virtual or unknown inputs, keep the engine path. Engine prewarm and readiness recovery are skipped while the macOS input is a Bluetooth headset and whenever the recorder will record the mic (`PinnedDictationInputPolicy.skipsEngineWarmup`, judged on the same selection the start makes), so a key press after a wake or route change never waits on an engine it won't record with; after a fallback to the engine (`PinnedDictationWarmupState`), warmup runs again until the recorder next starts. When the engine itself records a Bluetooth macOS input ("Same as macOS Sound settings", `PinnedDictationInputPolicy.engineRecordsBluetoothInput`), forced readiness recovery still skips warmup but replaces the dormant engine, which stays bound to the route from before the headset connected; building the new engine never reads `inputNode`, so the headset opens only at the key press. With the lid closed (`MacLidState`) the MacBook mic is never picked, and a pinned mic that delivers only exact zeros is swapped for another input. A wake mid-dictation interrupts it like the engine path. Falling back to the engine path reports `pinned_microphone_fell_back_to_engine`. The engine keeps one early branch each in start, stop, prewarm, readiness recovery, wake, config-change recovery, cancel and cleanup; sample admission duplicates the engine tap's so the tap closure stays where its source-text contract tests expect it
- `PinnedDictationSpeedPath.swift` — scores each take the pinned recorder made only for speed (plain built-in or wired mic, `PinnedDictationInputPolicy.recorderIsSpeedOnly`) once `STTRouter.transcribe` knows the result. Two empty takes in a row (no speech, signal with no words, or under 0.5 s of audio from a recorder open past the 1.5 s mis-tap limit) move that mic back to the engine path and the start click back to after recording starts, for the rest of the app version, and report `pinned_microphone_fell_back_to_engine` stage `empty_takes` with the take's channels, rate and bucketed gaps/drops/restarts. Added after one M1 MacBook Air got no words from any held dictation on 1.1.66's recorder while the engine worked on the same Mac. Takes the recorder is required for (a skipped Bluetooth input, a picked mic) are never scored. Local UserDefaults only (`pinned-dictation-speed-path`)
- `SharedMeetingMicClaim.swift` — pure claim/staleness types for the meeting-mic sharing handshake: `SharedMeetingMicClaim` carries a liveness probe from `MeetingSessionController` into `ParakeetEngine` so a claim can be told apart from a stale one left behind by an unexpected meeting teardown
- `SharedMeetingMicLevelMeter.swift` — dictation's waveform level while it borrows a meeting's mic: meters the relayed buffers with `DictationAudioLevelMeter` at about `audioMeteringInterval` (0.05 s). The meeting's engine tap delivers ~85 ms buffers, so a long buffer is split into ~interval windows shown at their offsets. The buffers are post-meeting-AGC (what dictation records), so levels can read a little hotter than the raw pinned path. The meeting's own published level (0.15 s, its own scaling) no longer feeds the dictation island; that made the waveform crawl while a meeting recorded. Runs on the relay queue, never the HAL thread; a session counter drops readings still hopping to the main actor after the borrow ends
- `SharedMeetingMicRecorder.swift` — thread-safe buffer for dictation samples borrowed from an active meeting's mic tap; `MeetingCaptureBridge` delivers PCM on its relay queue while `begin`/`append`/`finish`/`cancel` stay safe to call from `@MainActor` via an internal lock
- `ParakeetZombieEngineRecovery.swift` — `ParakeetEngine` extension: the startup audio watchdog that detects zombie engines (running but no usable signal after sleep/wake) and the separate generation-gated recovery task that replaces the stale `AVAudioEngine` through a bounded reset and retries once; the audio-graph/queue owner-token types those paths consult live in `ParakeetAudioGraphOwnership.swift`, not here
- `ParakeetSystemWakePolicy.swift` — pure decision for how `ParakeetEngine`'s system-wake handler reacts: skip tearing down the dormant audio graph while shared-meeting-mic dictation owns it, otherwise tear it down and mark an in-progress recording interrupted
- `ParakeetAudioDeviceLookup.swift` — `CoreAudioInputDeviceLookup`: CoreAudio default-input lookup, available-input enumeration, external-input-activity check, and dictation input selection descriptors used before Parakeet starts recording
- `ParakeetAudioEngineSupport.swift` — support types for Parakeet engine startup snapshots, retired-engine retention, and default-input listener teardown
- `ParakeetAudioGraphOwnership.swift` — the generation-gated owner-token types (`ParakeetAudioGraphOwnerToken`, `ParakeetAudioEngineQueueOwnerToken`, `ParakeetAudioStartAdmissionState`), timed-work lease bookkeeping (`ParakeetTimedAudioEngineWorkOwnership`), start-cancellation state, and the replaceable system-input work coordinator that `ParakeetEngine` constructs and consults on every start/stop path
- `ParakeetDecoderLayerCountCache.swift` — FluidAudio's decoder layer count, read once per loaded `AsrManager` (held weakly, compared by identity) instead of an actor round trip per inference; `ParakeetEngine` stores it next to `asrManager` and clears it with teardown
- `ParakeetTimedAudioEngineWorkLimiter.swift` — process-wide admission circuit for timed `AVAudioEngine` work; each acquired `Lease` holds its slot until the underlying CoreAudio call actually returns, even past its own timeout, so a permanently blocked call cannot let replacement workers pile up unbounded
- `WhisperEngine.swift` — app-owned WhisperKit STT engine used when advanced users select a Whisper model. Meetings send it batches of segments (`transcribeMeetingSegments`), decoded side by side through WhisperKit's batch API with the same options as one-by-one calls, so the text per segment doesn't change; `TRANSCRIPTED_MEETING_STT_PACKING=0` turns batching off along with Parakeet packing
- `WhisperCachedModelPolicy.swift` — `WhisperEngine` skips `WhisperKit.download` when a Transcripted-written manifest (`<whisper cache>/models/.transcripted/whisper-<variant>.json`, keyed to the app build) still matches the files on disk; a failed cached load falls back to download-then-load once
- `MeetingLanguageDetectionPolicy.swift` — reduces WhisperKit's per-window acoustic language observations (never transcript text) into detected / uncertain / multilingual; `WhisperEngine` requires agreement instead of inventing a runner-up margin
- `ASRInferenceWaiterQueue.swift` — `@MainActor` FIFO of callers waiting for `ParakeetEngine`'s ASR inference slot; cancellation removes only a pending waiter, and a handed-off caller owns (and must release) the slot
- `ModelLoadProgressWaiter.swift` — caller-owned wait on a model-download-state publisher with a deadline, used by `STTRouter.waitForRecordingModelLoadProgress`; finishing never cancels the shared model load
- `AppleSpeechEngine.swift` — macOS 26 on-device `SpeechAnalyzer`/`SpeechTranscriber` engine used when the user selects Apple Speech. Apple owns and downloads the per-language assets (`AssetInventory`); the engine has no language detection, so Auto means the Mac's first preferred language. Dictation transcribes Parakeet-recorded samples through `STTRouter.transcribeUsingExternalEngine`, like Whisper. Setup installs the Mac's language (dictation's) and then prefetches the saved meeting language; changing the Meeting language prefetches too. Downloads after setup publish only `languageDownload` (shown in the Meeting language row), never `modelDownloadState`, so a meeting language can't make the engine look unloaded. Apple caps reserved locales per app (`maximumReservedLocales`); the engine releases the least recently used one that isn't in use. A transcription failure clears the locale's installed mark so the next attempt re-asks Apple
- `AppleSpeechLocalePolicy.swift` — Foundation-only mapping from the app's bare meeting-language codes onto Apple's per-region locales (Mac region, then the region the Mac language's script implies such as zh-Hant → TW, then the language's home region, then a stable first match), plus which languages join result pieces without spaces; fast-tested
- `DictationAudioLevelMeter.swift` — normalizes live PCM buffers into a 0...1 level used by the dictation waveform UI. `DictationAudioLevelWindow` in the same file meters every buffer a recording delivers (one window per pinned recording / engine-tap start, fed on its capture queue) and hands back a `DictationAudioLevel` per ~1/30 s of audio (`TranscriptedConstants.dictationLevelReadingInterval`): the RMS of all of it plus the loudest buffer as `peak`. Capture-queue math only; it touches no engine or `inputNode`
- `DictationAudioLevels.swift` — the waveform's live reading (`DictationAudioLevel`): owned by `STTRouter` as a `let` and handed to `ParakeetEngine`, which fills it (`audioLevel` on the engine is a pass-through for the resets to silence). It stays off the router's `objectWillChange` because the Settings window and onboarding observe the whole router; a `@Published` level there re-rendered the window, Today page included, on every tick. The overlay subscribes to `readings`, delivered on the main actor with no second hop
- `DictationAudioRecovery.swift` — analyzes recorded dictation audio for usable speech signal and extracts focused, gain-normalized retry segments when an initial transcription attempt returns empty
- `DictationInputDeviceSelectionPolicy.swift` — follows the macOS input for normal dictation; the explicit faster-Bluetooth preference may recommend a built-in mic to avoid playback downgrades
- `PersistentDictationInputController.swift` — owns the explicit faster-Bluetooth-dictation preference at runtime: keeps the preferred non-Bluetooth system input selected, follows device reconnects, and restores prior input ownership across clean or unclean exits. Startup, reconnect, preference changes, and clean-exit restoration wait for external microphone capture to be idle; unknown process-activity reads defer writes, and skipped exit restoration keeps its durable recovery marker. Writes the system default input only through `DefaultInputDeviceMonitor.shared.setDefaultInputDevice(_:)` so its own writes are self-suppressed centrally. Everything outside the controller (monitor, HAL listener and lookups, prefs, reporting) comes in through `PersistentDictationInputSystem`; production always uses `.live` in `PersistentDictationInputController+Live.swift`, and `Tests/PersistentDictationInputControllerTests.swift` runs the real controller against fakes. Its device-list add goes through `PersistentDictationInputSystem.registerListener` (live: the same off-main queue, after the monitor's default-input add), and the first topology refresh is scheduled only once that add returns, so no reconcile or write runs before both listeners are live.
- `DefaultInputDeviceMonitor.swift` — the single `AudioObjectAddPropertyListenerBlock` registration for `kAudioHardwarePropertyDefaultInputDevice` (state is `@MainActor`; the add itself runs off main on `HALListenerRegistrationQueue` because at launch it is the app's first CoreAudio call and pays HAL client init, and callbacks are still delivered on main), shared by `PersistentDictationInputController`, `ParakeetEngine`/`ParakeetDeviceRecovery`, and `Sources/Meeting/MicActivityMonitor.swift` (previously three independent registrations with no ordering guarantee). Ordinary external changes fan out immediately without a redundant HAL read. A possible self-write echo uses a bounded, off-main ID lookup; subscribers receive each retained event in registration order with the centrally classified `isSelfWrite` flag. No observer is globally suppressed; each decides whether to react. The one-use expected-ID/deadline token is captured at callback admission, so a late A result cannot consume a newer B write marker; classification uses callback time, not delayed HAL-completion time. A burst while an echo is in flight retains at most the first event, earliest pending write echo, and latest remaining event. Do not register a fourth direct listener on this property — subscribe here instead.
- `DefaultInputDeviceMonitorSupport.swift` — testable types backing `DefaultInputDeviceMonitor`: the `DefaultInputDeviceSubscribing` protocol `MicActivityMonitor` depends on instead of the concrete singleton, the order-preserving observer registry and self-write tracker, and the bounded notification mailbox/timeout dispatcher. The monitor reuses its one process-lifetime coordinator across stop/start, so a blocked lookup can retain at most two timed-out worker threads; unknown results still notify observers conservatively as external changes, while late and closed-monitor results are discarded. Also holds `HALListenerRegistrationQueue` (one serial userInitiated queue for the launch-time default-input and device-list listener adds, with removes on main after their add) and `DefaultInputDeviceListenerRegistrar` (idle/registering/registered; start is a no-op unless idle, a stop while pending removes the same block when the add lands, and a failed add returns to idle so a later start retries).
- `DictationReadinessWaitPolicy.swift` — tiny policy that decides whether dictation should keep waiting for recovery, refresh input readiness, or start recording immediately
- `DictationStartReadiness.swift` — pure policy that decides, from whether Transcripted was the active app when the start was requested, how the start labels itself in diagnostics and whether it may escalate to the foreground-activation handshake. It deliberately carries no CoreAudio timeouts and no wait budget — see the header comment for why an earlier revision that did was wrong, and for what issue #1743 established versus what is still inference.
- `DictationRecordingStartOverlayPolicy.swift` — decides whether recording can skip the loading UI or should wait for microphone recovery, plus the start-failure cleanup, start-availability, stop-routing and early-release policies `DictationSession` consults (moved from `Sources/UI/Overlay/`)
- `DictationTrigger.swift` — what started or stopped a dictation (physical key, keyboard shortcut, menu, overlay button, onboarding, session cap); the raw values are telemetry values, and `DictationStartReadinessPolicy.hotkeyTriggerRawValues` must match them; also holds `DictationHotkeyRouter`
- `DictationProcessActivity.swift` — reference-counted `ProcessInfo.beginActivity` App Nap suppression held for the length of a dictation session. `DictationSessionController` balances it on `isDictating` transitions so every session-ending path releases it.
- `DictationSession.swift` — `@MainActor` engine-facing dictation orchestrator extracted out of `DictationSessionController`: owns the recovery wait-loop state machine (`waitForEngineAndStart`, merging the former `.startRecoveryRecording`/`.startRecording` duplicate paths), the model-warmup wait loop (`waitForModelAndStart`), `startDictationAudioRecording`, and the small STTRouter-touching cleanup/cancel helpers. Talks to `STTRouter` directly and reports back through outcome enums and injected status closures instead of touching overlay types, so `DictationSessionController` stays the only place that turns those into panel presentation.
- `DictationSessionTypes.swift` — `DictationSession`'s class declaration plus its pure, `TranscriptedAppState`-free nested types (`WaitStatus`, `StartOutcome`, `StartPathDecision`, ...); split out so `run-tests.sh` can compile and fast-test them without pulling in `TranscriptedAppState`'s whole-app dependency graph, the same constraint that keeps `DictationSessionController` itself out of the fast-test source list. `DictationSession` deliberately does not publish its own lifecycle/state enum — `DictationSessionController.isDictating` stays the single source of truth; see the NOTE at the top of this file for why an earlier `@Published var state` was removed.
- `ParakeetModelInitDiagnostics.swift` — builds safe diagnostic context for model-initialization failures without leaking transcript or user-content data
- `ParakeetPrewarmPolicy.swift` — central policy for deciding whether speech-engine input-readiness checks should proceed or be skipped based on microphone authorization state
- `ParakeetRecoveryState.swift` — pure-logic state machine for device-change recovery: generation counter (so stale recovery tasks can bail) and readiness flags (`isRecovering`, `inputFormatReady`) that the dictation overlay waits on instead of racing
- `ParakeetShortAudioGate.swift` — central policy for deciding when very short recordings should be dropped, surfaced as intentional empty results, or still transcribed
- `ParakeetInterruptionTerminal.swift` — the one way `ParakeetEngine` marks a recording interrupted: clears the restart flags, then publishes, and never sees the recorded timeline
- `PreparedRecordingConsumer.swift` — consumes a Stop's prepared snapshot only while its claim still names the current recording, so a late Stop can't clear a newer take
- `ExternalEngineTranscription.swift` — runs a Whisper or Apple Speech call under the recorded-transcription lease and releases it only after a thrown error is classified
- `ParakeetStartRecordingFailurePolicy.swift` — central recovery policy for invalid-format and audio-engine-start failures during recording startup
- `RecordedAudioTimeline.swift` — in-memory segmented audio buffer used when recorded audio needs to be preserved across interruptions or recovery handoffs
- `TranscriptionModelWarmupOwnership.swift` — balanced, generation-safe ownership state for disposable background model warmup versus active dictation/meeting/import use; shared runtimes resolve concurrent foreground work onto one concrete model
- `STTRouter.swift` — small main-actor wrapper used by the rest of the app
- `DictationLanguageScriptPolicy.swift` — flags dictation text that is nearly all (80%+, 4+ letters) one non-Latin script none of the person's languages use (Russian from an English speaker); Parakeet V3, Ultra and Whisper guess the language themselves. It runs for every model and ignores Latin-vs-Latin mixups. `DictationUserLanguages.swift` gathers those languages (Mac preferred languages, enabled keyboards, a chosen meeting language), read only when the text is flagged. `STTRouter.transcribe` holds the text in `heldBackDictationText` and reports `.otherLanguage`; the controller keeps the audio and offers Paste Anyway

- Dictation muffle ("Muffle other audio" in Settings): other apps keep playing, low-passed, while the dictation mic is open.
  - `DictationAudioMuffler.swift`: the coordinator, called by `DictationSessionController+Muffle.swift`. It runs the machine on one serial queue, performs its effects on the route, and is the only part that logs.
  - `DictationMuffleMachine.swift`: the pure timeline (inputs, effects, a virtual clock). Fast-tested.
  - `DictationMuffleRoute.swift`: the Core Audio objects. Tap A (unmuted, include-list) feeds the copy through a private aggregate on the output. Tap B (`.mutedWhenTapped`, include-list) in a tap-only aggregate is started only at the cut. Never change a running tap's mute behavior: coreaudiod restarts the IO and leaves a ~60 ms hole.
  - `DictationMuffleFilter.swift`: the sound (TPT cutoff glide plus output gate). It runs on the IO thread and is fast-tested.
  - `DictationMufflePolicy.swift` and `DictationMuffleHAL.swift`: the rules and fail-closed HAL reads.

## Current Notes

- Dictation muffle and Bluetooth: the muffle never opens an input device, `AVAudioEngine` or `inputNode`, so a Bluetooth headset as the default input is unaffected. It only builds its aggregate on outputs with no input streams; an unreadable count is refused. Starting a headset's input stream is what flips AirPods into call mode. On macOS 26, AirPods expose an output-only device plus a separate mic, so muffle works on them. It also stops on an output rate change.
- This directory powers dictation.
- `ParakeetEngine` consults `ParakeetPrewarmPolicy` before checking microphone input readiness. Idle readiness checks must not leave `AVAudioEngine` running, because that keeps the macOS microphone indicator active.
- `ParakeetEngine` consults `ParakeetShortAudioGate` before spending work on extremely short clips, so short-tap behavior changes belong here rather than in UI controllers.
- `ParakeetEngine` mirrors `ParakeetRecoveryState` flags into `@Published var isRecovering` and `@Published var inputFormatReady` (forwarded through `STTRouter`). `DictationSession.waitForEngineAndStart` distinguishes recovery, readiness refresh, and safe start. Startup resolves the tap format from the live node after applying voice processing: raw input uses the hardware input format; active VPIO uses its processed output format. Do not use `format: nil` to assume conversion of AirPods 24kHz hardware to a stale 48kHz output bus: a physical macOS 27 reproduction failed with `-10868`. Each retained buffer still keeps its delivered sample rate, and final inference/persistence resample each segment independently. Policy tests are not physical AirPods proof.
- `ParakeetEngine` consults `DictationInputDeviceSelectionPolicy` through `CoreAudioInputDeviceLookup` (in `ParakeetAudioDeviceLookup.swift`) before recording to follow the selected macOS input, including AirPods. Only the opt-in `PersistentDictationInputController` requests a built-in recommendation for faster Bluetooth starts. Every selection, including following a new default, must match the actual AUHAL binding before readiness is published; binding failures use bounded route settling instead of graph churn.
- Dictation must NEVER write the Mac-wide default input device (kAudioHardwarePropertyDefaultInputDevice) per session — microphone selection binds only the app's own AUHAL via `applyPreferredDictationInputDevice`. The 2026-08-24 Bluetooth audit found the old per-session write/restore cycle caused the AirPods route flip-flop, a ~470ms-vs-83ms start tax, audible playback perturbation, and (being untracked) silently killed `PersistentDictationInputController`'s ownership. `Tests/BluetoothRouteContractTests.swift` pins the negative invariant. The only legitimate Mac-wide input writes are `PersistentDictationInputController`'s, which go through `DefaultInputDeviceMonitor.shared.setDefaultInputDevice(_:)` for self-write suppression. Idle prewarm now always performs the real AUHAL bind + format readiness check (no Bluetooth-fallback deferral), so Bluetooth-route dictation starts from a genuinely settled graph; prewarm still must not leave `AVAudioEngine` running.
- `ParakeetEngine` consults `ParakeetStartRecordingFailurePolicy` when startup fails so format-reset, engine rebuild, and prewarm-retry behavior stay consistent across direct starts and recovery attempts.
- Recovery retains recording intent across notification bursts until the current generation finishes. Terminal interruption clears restart intent before publication but preserves captured audio for explicit recovery; retained audio alone must never restart capture or carry into a fresh dictation.
- Route-change analytics are committed only after the config-change debounce resolves to a new categorical route. Notification churn and A -> B -> A oscillation stay quiet. Input-device lookups use one latest-wins mailbox, and idle route changes only mark readiness stale; native graph recovery runs when a recording is active or when the user next starts dictation.
- Zombie-engine recovery owns a separate generation-gated task, replaces the stale `AVAudioEngine` through a timed reset, and retries once. Do not fold that task back into the startup watchdog or reuse the detected zombie graph.
- Timed `AVAudioEngine` work has a four-worker process-wide circuit. Each queued block keeps its lease until it actually returns, even after its caller times out, so permanently blocked CoreAudio work cannot create a fifth worker/graph. Retired native graphs also have a four-entry delayed-release cap while late callbacks drain; once either circuit is full, Transcripted fails closed instead of replacing again.
- Timed-out system-input CoreAudio writes have a two-worker circuit breaker. A first blocked queue may be replaced once; after two still-running operations, later route work fails immediately until a timed-out worker returns instead of accumulating blocked queues and threads.
- While that system-input circuit is open (`circuitOpenError`), `startRecording` fails before the pinned path the same way the snapshot's circuit-open failure does (same failure reason, readiness unready, prewarm retry), but with no pinned fallback, no graph rebuild, and the `audio_engine_work_circuit_open` error throttled to one per `audioStartFailureReportThrottle`. Without it the readiness wait (pinned prewarm marks ready because an unreadable route counts as a headset) turned every 100 ms poll into a fallback, an engine rebuild and a Sentry error until the stuck call returned (Sentry 3T/3V, 1.1.69).
- Default-input and audio-engine configuration notifications must dispatch recovery even when a CoreAudio route-selection lookup times out. Keep both notification lookups off the main actor and behind separate two-worker bounded circuits, and pass an explicit unknown route to recovery rather than retrying an unbounded detached HAL read. Unknown input is not proof of microphone readiness.
- `ParakeetEngine` stays `@MainActor` for app state, published UI state, and event reporting, but all `AVAudioEngine` graph work runs through its serial audio-engine queue (declared in `ParakeetEngine.swift` as `private(set)` so the sibling extension files can enqueue onto it; only the core file replaces it). Keep recording start/stop/readiness APIs async so callers do not block the main actor while CoreAudio settles, starts, stops, or rebuilds.
- The early-release error has exactly one producer: `DictationSessionController.cancelPendingDictationStartAfterEarlyRelease`, reached only when the user's own hotkey ends a session whose microphone start has not landed yet. `DictationEarlyReleasePresentationPolicy` picks its wording from the actual physical key action and elapsed milliseconds: a Push to Talk release under 250ms gets "Hold the key while you speak"; a Hands-Free second press keeps "Mic wasn't ready yet. Nothing was recorded." Both actions arrive as `trigger: physical_key`, so the trigger alone does not identify the mode. `ContextCaptureEngine` passes the actual shortcut action through dictation start and stop; UI retries omit the mode because they did not come from a physical key. Never infer it from the old `HotkeyPreferences.dictationShortcutMode()` setting, because current Settings stores separate bindings for both shortcuts. A start that exhausts `dictationRecoveryBudget` surfaces `microphoneTimeoutMessage` instead. The cancel event remains `.error` because that level is required for the local reliability record, PostHog's `reliability_failure_observed` count and Sentry forwarding, and every early release still gets all three except Sentry: `DictationEarlyReleaseCancelReport.forwardsToSentry` passes `forwardToSentry: false` for a tapped Push to Talk key (the same split as the message, via `DictationEarlyReleasePresentationPolicy.blamesMicrophone`), so Sentry only sees releases where the user was told the mic wasn't ready. Quick taps were most of Sentry issue 2J's volume. It sends only sanitized trigger, actual shortcut mode, pending stage, app active state and bucketed durations. The diagnostic key is `start_plan`, not `start_profile`, because the sanitizer drops keys containing `file`.
- A dictation start requested while Transcripted is NOT the active app may be slower than one from the menu. App Nap was one suspected mechanism, so `DictationSessionController.startDictation` takes the `DictationProcessActivity` assertion and picks a `DictationStartReadinessProfile` BEFORE audio work. Issue #1743's reported failures were later traced to quick Push to Talk taps, not a measured slow microphone stage; the App Nap assertion remains a preventive measure for other background starts, not a proven fix for that report. `pending_stage` and `stage_pending_for_ms` can distinguish future slow starts. Recovering *after* a failed background start was tried in PR #1744 and was not enough, so do not move the preparation back after the first microphone open.
- Do NOT widen the CoreAudio fences per start by setting "fence in flight" properties on `ParakeetEngine`. An earlier revision of the #1743 work did, and it was wrong twice: `ParakeetEngine` is `@MainActor` and a start suspends many times, so prewarm, `ParakeetDeviceRecovery` and `ParakeetZombieEngineRecovery` read the widened values whenever they interleave with a suspended start; and the recovery restarts (`ParakeetDeviceRecovery`, `ParakeetZombieEngineRecovery`, `ParakeetSharedMeetingMicBridge`) call `startRecording()` with the default, so later attempts silently dropped back to the foreground values. A per-start fence has to be threaded as a parameter through `audioInputSnapshot` and `runTimedAudioEngineWork`, and is worth doing only once a measurement says a stage actually needs it.
- `NSApp.isActive` read in `startDictation` means "was Transcripted frontmost the instant the start was requested", not "stays frontmost while the microphone opens". The menu path calls `sourceApp?.activate` on the line before, and AppKit activation is asynchronous, so a menu start samples as foreground and then hands focus away mid-start. That is intended: the sample stands in for "the process was in use a moment ago", which is what decides whether App Nap has had a chance to demote it.
- `ParakeetEngine` reports model-init failures with `ParakeetModelInitDiagnostics.failureContext(...)`, which keeps diagnostics useful for packaging/download/debugging issues without shipping raw transcript or device content.
- `scripts/ops/dictation-stop-autoeval.sh --encoder-compute cpu-and-gpu|all` is the local-only encoder compute comparison. Production keeps FluidAudio's default unless that benchmark process sets `TRANSCRIPTED_PARAKEET_ENCODER_COMPUTE_UNITS`.
- Don't move the Parakeet encoder to CPU + GPU in production. It was tried and rejected on 2026-09-27 (M5 Max, cold 4 s take): with the GPU idle it was only ~5 ms faster than the Neural Engine (88 vs 93 ms), but while another app kept the GPU busy it took 867 ms against the Neural Engine's 61 ms. People dictate during video calls and screen shares, so a busy GPU is the normal case. The rejected change was one line: `ParakeetModelLifecycle` passing `.cpuAndGPU` as the encoder's compute units by default.
- Only the final transcription is ever pasted or saved. The island's live words while you dictate come from a separate streaming engine, `LiveDictationCaptions` in Meeting (the same Parakeet EOU track as the meeting live transcript). Speech's only part is `DictationPreviewSampleSink`: while `STTRouter.setDictationPreviewSink` has one attached, both capture paths (engine tap, pinned-mic IOProc) append the same mono samples to it inside `pendingSamplesLock`, on their capture queue. Nothing new runs on a real-time thread and no engine or `inputNode` is touched, so a Bluetooth headset as the default input sees no change. The sink is nil unless a preview is listening, and the final pass never reads it. It resamples to 16 kHz with one `AVAudioConverter` kept across reads (low-passed, not the linear `AudioResampler`), and past 30 s unread it drops everything unread so the capture queue's work stays constant. The old provisional-text path stays removed; don't revive dormant audio-tap branches.
- `DictationAudioLevelMeter` converts live audio buffers into normalized meter levels using `TranscriptedConstants` floor and ceiling thresholds. Keep waveform calibration changes here instead of burying them in overlay code. Both capture paths meter every buffer through `DictationAudioLevelWindow` (the old once-per-50 ms sample skipped ~80% of the audio) and send each reading to `audioLevels` with one hop to the main actor; the island's bars move on their own display clock (`NotchIslandLevelScroller`), not once per reading.
- `DictationAudioRecovery` analyzes buffered audio for usable speech signal (peak, RMS, active ratio) and can produce a focused, gain-normalized retry segment. `ParakeetEngine` uses it to retry transcription when an initial attempt returns empty rather than silently dropping audio that contained real speech.
- The meeting pipeline reuses the same app-owned `STTRouter` through `Sources/Meeting/MeetingSTTAdapter.swift`.
- Do not assume a separate local-LLM drafting path exists in this tree.
